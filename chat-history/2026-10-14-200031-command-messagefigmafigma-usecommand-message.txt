  7. Recommended additions

  These are not in the brief. I included them because the brief grades judgment,
  and each one closes a gap or a likely failure.

  Backend correctness

  - Storage must survive serverless. On Vercel and Netlify the filesystem is
    ephemeral, so a file or local SQLite loses leads. Use a hosted store: Turso
    (SQLite), Upstash Redis, Cloudflare D1 or Vercel Postgres. This is the most
    likely hidden trap in the task, and it belongs in the README.
  - Atomic dedupe. Concurrent serverless instances defeat an in-memory check.
    Use a unique key phone:<E.164> with a 10-minute TTL (Redis SET NX EX 600, or
    a unique constraint plus a time window). Return the original lead's success
    response on a duplicate, so the user sees success, not an error.
  - Client-side double-click guard. Disable the button while the request is in
    flight, and send an idempotency key per form instance.
  - Phone normalization. Accept +375 29 123-45-67, 80291234567, 375291234567 and
    29 1234567. Store E.164 (+375291234567) and apply a mask while typing.
    Mobile codes are 25, 29, 33 and 44. Decide in the README whether Minsk
    landlines (17) are allowed. A callback form usually wants mobiles only.
  - Server-side validation duplicates every client check (name length, phone,
    enum for interest, comment length cap).
  - Spam defense: honeypot field, minimum fill time, and IP rate limiting. Skip
    CAPTCHA because it hurts conversion.
  - Delivery-failure UX: an inline error with a retry button, plus a fallback
    phone number and a Telegram/Instagram link. Keep the typed form values on
    failure.
  - Retry safety: because of the idempotency key, a retry after a timeout must
    not create a duplicate.

  Attribution

  - Capture utm_source, utm_medium, utm_campaign, utm_content and utm_term.
  - Capture click IDs: yclid (Yandex Direct), ysclid, fbclid (Instagram/Meta).
  - Capture landing URL, document.referrer and a submit timestamp.
  - Persist them at first load in sessionStorage or a first-party cookie, so
    they survive navigation and anchor jumps. Keep first-touch values.
  - Send them as hidden fields in the lead payload, and show them in the
    Telegram message.

  Telegram duplication

  - Send a formatted message: name, phone, interest, comment,
    source/campaign/ad, landing page, time.
  - Keep the token in an environment variable and never commit it. Telegram
    failure must not fail the lead: save first, notify second.

  - "Next roast" block: countdown to Thursday's roast and Friday's delivery. It
    shows freshness instead of claiming it.
  - Order cutoff for Friday delivery. The brief gives none, so state your
    assumption (for example "orders by Wednesday 20:00").
  - Open-now indicator computed from the hours, in Minsk time.
  - Delivery rules: the brief only says "free from 50 BYN". State what happens
    below that, and mark your assumption.
  - Subscription pricing check. Two Brazil bags at 26 BYN cost 52, less than 54.
    Explain what the 54 BYN buys (free delivery, choice of beans) or adjust the
    offer, and note it in the README.
  - Order intent pre-fill: "Subscribe" and "Order" buttons on product cards
    select the matching interest in the form and scroll to it.
  - Sticky mobile CTA, since most traffic is mobile.
  - Click-to-call and a map link (Korolya 9) with pickup hours.
  - FAQ: grind options, how to store beans, how freshness is measured, how to
    cancel the subscription.
  - Consent line under the form for personal data processing (name, phone),
    linked to a short privacy note. Check the wording against Belarusian
    data-protection requirements.
  - Thank-you state after submit: what happens next ("we call within X hours")
    with a working-hours caveat.

  Design (the stated main criterion)

  - Choose a concrete visual idea tied to this client (Thursday roast, 5 kg
    batches, Minsk) before touching AI. Write it down in the README.
  - Avoid default tells: purple gradients, stock-card grids, generic hero with
    centered text, emoji bullets, uniform rounded cards.
  - Pick a deliberate type pair and palette. Warm, plain, not glossy.
  - Use real, consistent photography, or a deliberate illustrated or typographic
    approach. A text logo is allowed, so make it good.
  - Write specific copy with the facts above. Rewrite weak generic lines.
  - Review each AI pass manually and keep notes on what you changed. That feeds
    the README.

  Performance and quality

  - Target mobile Lighthouse 90+ in all four categories.
  - Optimize images (modern formats, explicit dimensions, lazy loading below the
    fold), self-host fonts with font-display: swap, and avoid layout shift.
  - Animations: CSS or lightweight JS, honor prefers-reduced-motion, and keep
    them off the critical path.
  - Accessibility: labels bound to inputs, visible focus, 4.5:1 contrast, error
    messages tied to fields, lang="ru".
  - SEO and sharing: title, description, Open Graph and Twitter tags with a
